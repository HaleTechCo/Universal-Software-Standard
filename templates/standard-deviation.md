# Standard Deviation: USS-<PREFIX>-<NNN>

<!--
Copy this file once for each deviation, for example to
docs/standard-deviations/USS-<PREFIX>-<NNN>.md. Replace each instruction
with your text. Then add the deviation to `deviations` in .uss/record.yaml,
with the same rule, approver, date and review-by date. A deviation from a
MUST or MUST NOT rule makes the project not compliant. See section 9 of
standard/conventions.md.
-->

## Rule

Write the ID and the title of the rule that the project does not follow.

## Level

Write the level of the rule: MUST, MUST NOT, SHOULD or SHOULD NOT.

## USS version

Write the USS version that the project's record pins, for example 0.1.0.

## Scope

Write exactly what the project does not follow, and where: which part of the rule, and which components, files or environments.

## Reason

Write why the project does not follow the rule.

## Risks and impact

Write the risks that the deviation causes, and who or what they can affect.

## Compensating controls

Write the measures that reduce those risks, or write "None".

## Approval

Follow your organisation's approval policy.

- **Approver:** Write the name and role of the person who approved the deviation.
- **Date:** Write the approval date as YYYY-MM-DD.

## Review by

Write the date of the next review of this deviation as YYYY-MM-DD.

## Remediation plan

Write how and when the project will follow the rule, or write "None".
