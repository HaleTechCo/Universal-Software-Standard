# Dependencies

- **Prefix:** DEP
- **Kind:** area
- **Applies when:** has-dependencies

This area covers the third-party code that a project declares, resolves,
checks and updates: packages from registries, libraries from other
repositories and vendored code. The project's own packages (workspace
members, and path dependencies inside the repository) are not dependencies for
this area. Its rules count toward Safety by default. Language modules and vendor profiles name each ecosystem's syntax and tools;
the tools named here are examples only. Toolchains, CI components, container
images and SBOMs are in the Supply chain area (SUP).

## Declaring and resolving

### USS-DEP-001: Bound every version range

- **Level:** MUST
- **Applies when:** always
- **Category:** Safety
- **Verify:** Read every manifest. Each dependency has a version requirement
  that admits at most one major version (an exact version, or a range that
  stops before the next major version). A requirement that is `*`, `latest`,
  a branch name, or a lower bound with no upper bound (an unbounded `>=`) is a
  failure. Where the ecosystem has a default range syntax, read it by the
  ecosystem's rules: for example `1.2` in Cargo means `>=1.2.0, <2.0.0`, and
  `~=1.2` in Python means `>=1.2, ==1.*`.
- **References:** The Cargo Book, Specifying Dependencies (docs read
  2026-11-23); Python Packaging User Guide, Version specifiers (Compatible
  release, docs read 2026-11-23); Apache Maven Enforcer, Version Ranges (docs
  read 2026-11-23)

Every dependency in every manifest MUST be limited to a bounded range no wider
than one major version (a "soft pin"), and never `*`, `latest`, a branch or an
unbounded `>=`. A manifest is a file that declares the dependencies of a
project, such as `Cargo.toml`, `package.json`, `pyproject.toml` or `pom.xml`.
Examples of such a range are `1.2` in Cargo, `^1.2.0` in npm, `~=1.2` in
Python and `[1.2,2.0)` in Maven.

**Rationale:** A range with no upper bound accepts a new major version, which
can break the build or bring in changed or hostile code without any change to
the project. A bounded range keeps updates within the versions that the
project expects.

### USS-DEP-002: Commit a lockfile

- **Level:** MUST
- **Applies when:** always
- **Category:** Safety
- **Verify:** The repository holds a lockfile (or each lockfile that the
  ecosystem needs) in version control, and it records an integrity hash for
  every package that it resolves. Read the lockfile: an entry for a package
  fetched from a registry or an archive that has no integrity hash is a
  failure. A git dependency pinned to a full commit hash counts as
  integrity-pinned. Examples of such files are `package-lock.json` (an `integrity`
  field per package) and Go's `go.sum` (a hash per module).
- **References:** npm Docs, package-lock.json (v10, docs read 2026-11-23); Go
  Modules Reference, go.sum files (docs read 2026-11-23)

A lockfile with an integrity hash for every resolved package MUST be
committed. A lockfile is a file, generated by the package manager, that
records the exact version of every direct and transitive dependency that the
manifest resolves to.

**Rationale:** The manifest allows a range of versions, so two builds can
install different code. The lockfile fixes the versions, and its hashes show
that the code installed is the code that was resolved.

### USS-DEP-003: Install only from the lockfile

- **Level:** MUST
- **Applies when:** always
- **Category:** Safety
- **Verify:** Read the build scripts and CI configuration. Every step that
  installs or builds with dependencies uses the lockfile as it stands, and the
  step fails when the lockfile is out of date with the manifest. Examples of
  such commands are `cargo build --locked`, `npm ci` and `uv sync --locked`.
  A step that resolves versions afresh (such as `npm install`, or a build that
  may rewrite the lockfile) is a failure.
- **References:** The Cargo Book, cargo build (--locked, docs read
  2026-11-23); npm Docs, npm ci (v10, docs read 2026-11-23); uv Docs, Locking
  and syncing (docs read 2026-11-23)

Builds and CI MUST install strictly from the lockfile, and MUST fail when it is
out of date. Examples of commands that do this are `cargo build --locked`,
`npm ci` and `uv sync --locked`.

**Rationale:** An install that can update the lockfile silently takes in new
versions, so the lockfile no longer describes what was built and tested.

### USS-DEP-004: Declare direct dependencies

- **Level:** MUST
- **Applies when:** always
- **Category:** Safety
- **Verify:** Compare the packages that the code, tests and build files
  import or call with the manifest. Each one is declared there. A package that
  is used and appears only in the lockfile or in the manifest of another
  package is a failure. Tools such as deptry, knip, Maven `dependency:analyze`
  (the "used undeclared" group) or `go mod tidy` report this, but each one
  sees only part of the code, so a clean report is partial evidence.
- **References:** deptry README (docs read 2026-11-23); Knip, Unused
  dependencies (docs read 2026-11-23); Apache Maven Dependency Plugin 3.11.0,
  dependency:analyze; Go Modules Reference, go mod tidy (docs read 2026-11-23)

Every package that the code uses directly MUST be declared as a direct
dependency, and never reached through another package's dependencies. A
package is used directly when the project's code, tests or build files import
or call it.

**Rationale:** A package that is reached through another package's
dependencies can disappear or change version when that other package changes,
and the project does not see it happen.

### USS-DEP-005: Separate runtime, build and development dependencies

- **Level:** MUST
- **Applies when:** always
- **Category:** Safety
- **Verify:** Each manifest declares runtime, build and development
  dependencies in separate groups (such as `dependencies`, `devDependencies`
  and build requirements). A dependency that only tests, linters or build
  tools use is not in the runtime group.
- **References:** none

Runtime, build and development dependencies MUST be declared separately, in
order that shipped artifacts carry only runtime ones. A runtime dependency is one
that the program needs while it runs. A build dependency is one that is needed
only to build it, and a development dependency is one that only tests, linters
and other tools use.

**Rationale:** Each extra package in a shipped artifact is more code to
attack and to keep updated, and it brings its own vulnerabilities.

### USS-DEP-006: No end-of-life dependencies

- **Level:** MUST NOT
- **Applies when:** always
- **Category:** Safety
- **Verify:** For the release line of each dependency in the lockfile (the
  major or minor series that the supplier's support policy defines), the
  supplier's support policy, release history or registry notice (such as a
  deprecation or archive notice) shows that the line still receives security
  fixes at the audit date. Where none of these shows it, the auditor records
  `unverified`. A scan that flags end-of-life or unmaintained packages is
  partial evidence.
- **References:** CWE-1104, Use of Unmaintained Third Party Components (CWE
  4.20, page read 2026-11-23); NIST SP 800-218 (SSDF 1.1) PW.4.4 (notional
  example on checking that a component is maintained and has not reached end
  of life)

A project MUST NOT use a dependency at a version that no longer receives
security fixes. A version is end-of-life when the release line that it belongs
to (the major or minor series, as the supplier's support policy defines it) no
longer receives security fixes from its supplier, as the support policy,
release history or deprecation notice shows.

**Rationale:** A flaw found in a version that is not fixed stays in every
project that uses it.

## Vulnerabilities

### USS-DEP-007: Scan dependencies for known vulnerabilities

- **Level:** MUST
- **Applies when:** always
- **Category:** Safety
- **Verify:** The CI configuration has a job that scans the dependencies,
  read from the lockfile or the resolved dependency graph so that transitive
  ones are included, against a database of known vulnerabilities. The job runs
  on each pull request and each push to the default branch, and on a schedule
  trigger. A scanner that reads only the manifest, or only direct
  dependencies, is a failure. Without access to the CI configuration, the
  auditor records `unverified`.
- **References:** NIST SP 800-218 (SSDF 1.1) RV.1.1; OSV schema 1.9.2 (a
  format for vulnerability data that scanners read)

CI MUST scan all dependencies, direct and transitive, for known
vulnerabilities on every change and on a schedule. Every change means each
pull request and each push to the default branch. A scheduled scan finds a
vulnerability that is published after the last change.

**Rationale:** Vulnerabilities in a dependency are found and published after
the project has used it, so a check that runs only when the code changes
misses them.

### USS-DEP-008: Fix or assess each known vulnerability

- **Level:** MUST
- **Applies when:** always
- **Category:** Safety
- **Verify:** Take the result of the dependency scan of DEP-007 for the
  audited commit (the latest CI run, or a run of the scanner). Every finding
  it reports is fixed (the dependency is at a version that the finding does
  not cover), or the scanner reads a recorded assessment for it (such as an
  ignore entry or a VEX statement in the file that the scanner is configured
  to read) that says why the product is not affected. A recorded assessment
  without a reason is a failure. Where the tool supports an expiry date, so is
  one with no expiry date, and so is one past its expiry date. A finding that is neither fixed nor assessed is
  a failure.
- **References:** NIST SP 800-218 (SSDF 1.1) RV.2.1, RV.2.2; OSV schema 1.9.2
  (a format for vulnerability data that scanners read)

Each known vulnerability that the scan reports MUST be fixed, or assessed as
not affecting the product with the reason recorded where the scanner reads it.
The target is that the scan has no open findings. Each recorded assessment
gives a reason and, where the tool supports it, an expiry date, so that it is
reviewed again.

**Rationale:** A scan that nobody acts on does not lower the risk, and an
assessment with no reason cannot be checked or reviewed.

## Sources

### USS-DEP-009: Protect private package names

- **Level:** MUST
- **Applies when:** uses-private-packages
- **Category:** Safety
- **Verify:** For each private package that the project uses, the package
  manager configuration binds its name to the private registry (for example an
  npm scope that is mapped to the private registry), or the private registry
  is the only source that is configured and does not serve public versions of
  that name (a private registry that proxies a public one does not meet this),
  or the registry blocks public versions of a name it holds (for example Azure Artifacts with external
  versions not allowed for that package). A private package name that the
  package manager can also resolve from a public registry is a failure.
- **References:** Alex Birsan, Dependency Confusion: How I Hacked Into Apple,
  Microsoft and Dozens of Other Companies (2021-02-09); npm Docs, About scopes
  (docs read 2026-11-23); Microsoft Learn, Safeguard against malicious public
  packages - Azure Artifacts (ms.date 2025-10-21)

Private packages MUST be scoped, or their registry MUST be configured, so that
a public package with the same name cannot replace them.

**Rationale:** When the same name exists in a public and a private registry,
the package manager can take the public package, so anyone can publish code
under the name of a private package. Dependency confusion is the name for this
attack.

### USS-DEP-010: Treat vendored code as a dependency

- **Level:** MUST
- **Applies when:** vendors-dependencies
- **Category:** Safety
- **Verify:** For each directory or file of third-party code in the
  repository, a record (in the code's own metadata, a vendor list or a
  manifest entry) names the upstream version it is pinned to, its source and
  its licence. The dependency scan of DEP-007 covers the vendored code, and a
  change history or an update pull request shows that it is updated like any
  other dependency.
- **References:** none

Vendored code MUST be pinned to an upstream version, its source, version and
licence MUST be documented, and it MUST be scanned and updated like any other
dependency. Vendored code is third-party source or binaries that the
repository holds and builds or ships.

**Rationale:** Vendored code has no package manager to track its version, so
without these records it is scanned and updated by nobody.

## Choosing and maintaining

### USS-DEP-011: Document each direct dependency

- **Level:** SHOULD
- **Applies when:** always
- **Category:** Safety
- **Verify:** Each direct dependency has its purpose written down, in a comment
  in the manifest or in a dependency list in the repository. For a dependency
  that was added since the last recorded audit (or in the last 12 months when
  there is no earlier audit), the change that added it carries that record.
- **References:** none

The purpose of each direct dependency SHOULD be recorded, in the manifest or a
dependency list, when it is added.

**Rationale:** A later reader can only judge whether a dependency is still
needed, or can be replaced, if its purpose is written down.

### USS-DEP-012: Check health before adding

- **Level:** SHOULD
- **Applies when:** always
- **Category:** Safety
- **Verify:** For each dependency added since the last recorded audit (or in
  the last 12 months when there is no earlier audit), the pull request, the
  commit or the dependency list shows that the dependency was checked for the
  stated properties before it was added, and that the standard library was
  preferred where it was enough. Where no record shows the check, the auditor
  records `unverified`.
- **References:** none

Before a dependency is added, it SHOULD be checked to be maintained, not
deprecated or archived, licence-compatible and with more than one maintainer,
and the standard library SHOULD be preferred when it is enough.

**Rationale:** A dependency that nobody maintains, or that one person
maintains, is a risk that the project takes on with every release it ships.

### USS-DEP-013: Remove unused dependencies

- **Level:** SHOULD
- **Applies when:** always
- **Category:** Maintainability
- **Verify:** Each declared dependency in each manifest is in use. Tools such
  as deptry, knip, Maven `dependency:analyze` (the "unused declared" group) or
  `go mod tidy` report unused ones, but each sees only part of the use, and
  Maven's default analysis works on bytecode and misses reflection, so a clean
  report is partial evidence. The auditor checks each reported dependency in
  the code, build files and configuration.
- **References:** deptry README (docs read 2026-11-23); Knip, Unused
  dependencies (docs read 2026-11-23); Apache Maven Dependency Plugin 3.11.0,
  dependency:analyze; Go Modules Reference, go mod tidy (docs read 2026-11-23)

Every declared dependency SHOULD be in use. A dependency is in use when the
project's code, tests, build files or configuration refer to it, or the
program loads it at run time (for example by reflection or a plugin lookup).

**Rationale:** An unused dependency adds code to build, scan and update, and
adds attack surface, and it gives nothing back.

### USS-DEP-014: Automate dependency updates

- **Level:** SHOULD
- **Applies when:** always
- **Category:** Safety
- **Verify:** The repository holds the configuration of an update tool (such
  as `renovate.json` or `.github/dependabot.yml`) that covers every manifest.
  The dependency updates merged since the last recorded audit (or in the last
  12 months when there is no earlier audit) were opened as pull requests by the
  tool.
- **References:** Renovate Docs, Configuration options (docs read 2026-11-23);
  GitHub Docs, Dependabot options reference (docs read 2026-11-23)

Dependency updates SHOULD arrive as automated pull requests (such as from
Renovate or Dependabot).

**Rationale:** Small updates that arrive often are easier to review and test
than a large update after a long gap, and security fixes reach the project
sooner.

### USS-DEP-015: Wait before adopting a new release

- **Level:** SHOULD
- **Applies when:** always
- **Category:** Safety
- **Verify:** The configuration of the update tool sets a minimum age for new
  releases of at least three days: for example Renovate `minimumReleaseAge`,
  or Dependabot `cooldown` (`default-days`), or a resolver setting such as uv
  `exclude-newer` given as a duration. Dependabot `cooldown` does not apply to
  security updates, so it is partial evidence: the auditor checks the
  security-update pull requests directly. Where no tool sets a minimum age,
  the auditor records `fail`.
- **References:** Renovate Docs, minimumReleaseAge (docs read 2026-11-23);
  GitHub Docs, Dependabot options reference (cooldown, docs read 2026-11-23);
  uv Docs, Resolution (exclude-newer, docs dated 2026-11-05)

A newly published dependency release SHOULD be adopted only after a minimum age
of a few days, set in the update tool. A few days means at least three days.
The update tool is the tool that picks new versions: an update bot, or the
package manager's resolver.

**Rationale:** A malicious or broken release is usually found and withdrawn
within days of publication, so a delay keeps the project clear of most of
them.

## Libraries

### USS-DEP-016: Declare the widest tested range

- **Level:** SHOULD
- **Applies when:** is-library
- **Category:** Safety
- **Verify:** For each dependency of the library, the lower bound of the
  declared range is the lowest version that CI installs and tests (the lowest
  version of DEP-017). A lower bound above or below that version is a failure.
  The upper bound follows DEP-001: it is the bound that DEP-001 sets, and the
  auditor does not require it to equal the newest version tested.
- **References:** none

A library SHOULD declare the widest range of each dependency that it is tested
against, within the bound of DEP-001. Tested against means that CI installs the
version and runs the library's tests.

**Rationale:** A range that is narrower than the tested one forces the
library's users into version conflicts with their other dependencies.

### USS-DEP-017: Test the lowest versions

- **Level:** SHOULD
- **Applies when:** is-library
- **Category:** Safety
- **Verify:** The CI configuration has a job that installs the lowest version
  that each dependency range allows, and runs the tests against it, as well as
  the job that runs against the newest versions.
- **References:** none

CI SHOULD test the library against the lowest version in each dependency range,
as well as the newest.

**Rationale:** The declared lower bound is a claim that the library works with
that version, and only a test of that version shows whether the claim holds.
